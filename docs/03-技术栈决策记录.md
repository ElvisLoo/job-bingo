# ADR-001 · 桌面端框架选型：从 Tauri 改为 Electron

- 状态：**已采纳**（v0.2 起生效，推翻 v0.1 结论）
- 日期：2026-10-26
- 决策者：罗广 / AI 助理
- 影响范围：桌面端外壳、移动端外壳、共享代码组织方式

---

## 1. 背景：什么变了

v0.1 的选型建立在三个前提上：

1. 音频采集在 **Windows 端**（WASAPI Loopback 双轨）
2. 需要**低延迟实时音频处理**（Rust 的强项）
3. 桌面端是主战场，手机是配件

v0.2 的需求澄清把这三点全部推翻了：

1. 音频采集在 **手机端**（手机麦克风听笔记本外放）
2. 手机上只做采集 + 判定 + 编排，**重活交给云端 API**
3. 电脑端是**纯渲染终端**——不碰音频、不碰麦克风权限、只收一段 JSON 画字

> 关键推论：**桌面端 90% 的工作量变成"渲染 + 网络 + 窗体"。** Rust 的实时性能优势在这里用不上，而它的开发成本照付。

---

## 2. 用户提出的质疑（必须先回答）

> "我记忆中 Electron 腾讯也都在用，这个跨平台技术好像挺厉害的，就是软件包好像有点大，包括微信和 QQ 好像都已经用了这个技术栈。"

**基本属实，但有个反向趋势值得注意：**

| 产品 | 实际情况 |
|---|---|
| QQ NT 桌面版 | ✅ 基于 Electron（2022 年重构时采用） |
| 腾讯文档、部分腾讯客户端 | ✅ Electron 系 |
| VS Code / Slack / Discord / Figma / Notion / Obsidian | ✅ 全部 Electron |
| **微信 4.0 桌面版** | ⚠️ 据公开信息已从 Electron 迁出，改用自研跨平台框架，**动因正是包体与内存** |

所以"Electron 很厉害"是对的，"腾讯都在用"对了一半——腾讯恰恰是**踩过坑之后正在往回走**的那一家。包大、内存高是真问题，不是偏见。

---

## 3. 候选方案对比

| 维度 | Electron + Capacitor | Tauri 2 全栈 | Electron + Kotlin 原生 |
|---|---|---|---|
| 桌面包体 | 90–150 MB | 8–15 MB | 90–150 MB |
| 桌面内存 | 250–400 MB | 80–150 MB | 250–400 MB |
| Android 方案 | Capacitor（成熟） | Tauri 2 mobile（2024 GA，生态薄） | Kotlin 原生（体验最好） |
| **前端代码复用** | ✅ React 一套 | ✅ React 一套 | ❌ 两套 |
| **业务逻辑复用** | ✅ TS core 三端共享 | ⚠️ Rust core 不能给 Android WebView 用 | ❌ 两套 |
| 透明置顶窗体 | `transparent` + `setIgnoreMouseEvents` + `setBackgroundMaterial('acrylic')`，Windows 11 原生亚克力一行代码 | 支持，但混合 DPI 有已知问题，亚克力要自己调 DWM API | 同 Electron |
| 音频能力 | 强（Node 原生模块 / FFI） | 最强（直调 WASAPI） | 强 |
| 上手成本 | 低（JS/TS） | 高（Rust + FFI + 交叉编译） | 中（Kotlin + JS 双栈） |
| 生态与现成轮子 | 极多 | 少 | 中 |
| 调试体验 | Chromium DevTools 全量 | 需 Rust 调试链 | 双端分离调试 |

---

## 4. 决策

> **桌面端 Electron + 手机端 Capacitor + 共享 TypeScript Core。**

```
pnpm workspace
├─ packages/core        ← LLM 网关、提示引擎、简历解析、配对协议（纯 TS，零平台依赖）
├─ apps/desktop         ← Electron + React：半透明悬浮窗、快捷键、托盘
└─ apps/mobile          ← Capacitor + React：录音、ASR、思路卡、模式切换
                              └─ android/  ← Kotlin 插件：AudioRecord、前台服务、MediaProjection
```

### 三条关键理由

1. **采集在手机，桌面不碰音频** → Rust 的性能优势失去用武之地，而它的学习曲线一分不少。这是决定性的一条。
2. **一套 TypeScript 三端共享** → LLM 网关、提示引擎、简历解析这三块是产品真正的含量所在，写成纯 TS 后桌面和手机直接复用，不用写两遍。Tauri 的 Rust core 无法被 Android WebView 调用，这部分要么重写要么走 FFI，得不偿失。
3. **半透明窗体是 Electron 的舒适区** → `setBackgroundMaterial('acrylic')` 在 Windows 11 上一行代码出亚克力效果；`setIgnoreMouseEvents(true, { forward: true })` 实现点击穿透；`setAlwaysOnTop(true, 'screen-saver')` 保证盖住全屏会议窗口。这些都是 Electron 里被验证过一万次的路径。

### 代价，以及怎么缓解

| 代价 | 缓解 |
|---|---|
| 包体 ~120 MB | 用 electron-builder 分架构打包 + NSIS 压缩；可接受（微信安装包 200MB+，用户对桌面软件包体容忍度高于想象） |
| 内存 300 MB 起 | 悬浮窗用独立 `BrowserWindow`，长时间不用的会话窗口销毁重建；关掉不需要的 Chromium 特性（`--disable-gpu-compositing` 视情况） |
| 冷启动 1–2s | 托盘常驻 + 开机自启（可选），避免每次重启 |
| Electron 无 Android | 用 Capacitor，前端复用，只有录音/前台服务/投屏需要写 Kotlin 插件 |

---

## 5. 什么情况下回退到 Tauri（迁移触发条件）

架构上已为此预留：**窗体层极薄，业务全在 `packages/core`**。若出现以下任一情况，只重写外壳即可，业务代码不动：

1. 需要在 **PC 端直接抓系统声音**（做双轨分离或"高质量模式"）——Rust 直调 WASAPI 明显优于 Node FFI
2. 包体/内存成为主要用户投诉（例如发布到 winget 或应用商店时）
3. Tauri 2 的 Android 生态补齐了音频与前台服务插件

---

## 6. 记录在案的错误判断

v0.1 里我把"实时音频处理"当成了本项目的核心难点，因此选了 Rust。**这个判断错在把技术难度当成了架构重心。** 真正的重心是"手机能不能听清楚 + 提示够不够快 + 内容够不够准"，前两者跟框架关系不大，后者是 prompt 工程的事。

选型的第一原则不是"哪个技术更强"，而是"哪个技术让这个产品的核心难点更容易被解决"。

# ADR-002 · 采集端双轨化后的框架复核

- 状态：**复核结论——维持 Electron，但补一个 Rust sidecar**
- 日期：2026-10-26
- 触发：「手机和电脑都要识别语音内容」

## 1. 什么被推翻了

v0.2 的核心假设是"采集只在手机"。用户澄清：**两端都要能采能识**，理由是电脑直接抓系统声音延迟更低。

这条澄清是对的，而且比"延迟"本身更有价值：

- 电脑走 WASAPI 回环 = **数字直采**，音质接近无损，不受房间混响影响
- 回环轨 = 对方、麦克风轨 = 自己，**说话人天然分离，不用猜**
- 没有手机也能用（**单机模式**），产品可用性大幅提升

ADR-001 §5 写的"迁移 Tauri 的触发条件"第一条正是"需要在 PC 端直接抓系统声音"。**这个触发器现在被触发了**，所以必须复核，不能装作没看见。

## 2. 复核结论：不整壳迁移，只加一个 sidecar

### 为什么不全迁 Tauri

| 考虑 | 判断 |
|---|---|
| 收益 | 包体从 120MB 降到 15MB，内存在 300MB 降到 120MB |
| 成本 | 全壳重写 + Rust 生态重建（托盘、快捷键、多显示器、WebContentsView 全要重做） |
| 关键 | **本项目只有一个地方需要 Rust：拿 PCM。** 其余全是 UI 与网络 |
| 结论 | 为 200 行采集代码重写整个外壳，不划算 |

### 为什么需要一个 sidecar，而不是纯 Electron

Electron 其实**能**抓系统声音：`session.setDisplayMediaRequestHandler` 里给 `audio: 'loopback'`。但有两个硬伤：

1. **必须同时请求屏幕视频轨才能拿到音频** → 意味着要抓屏。对一个承诺"只听不看"的产品，这是糟糕的隐私观感。
2. **双轨同步难做**：loopback 走 Chromium 媒体栈，麦克风走 getUserMedia，两路时间戳不在同一时钟上，对齐误差可达几十毫秒。

所以：

- **M1 起步**：先用内建 loopback 跑通，验证"能不能抓到声、延迟多少"，1 天工作量，风险最低。
- **M1 通过后**：替换为 Rust sidecar（约 200 行，`windows` crate 直调 WASAPI），双轨共享同一时钟，独立进程，崩溃可自动拉起。

### sidecar 的接口设计

```
capture-agent.exe --loopback-device default --mic-device communications
   stdout: 二进制帧 [track:u8][timestamp_us:u64][len:u32][pcm16...]
   控制:   stdin 接收 JSON 命令（start/stop/switch-device/list）
```

独立进程的好处：崩溃不影响 UI、可以用不同音频栈、将来若要换成 Tauri 也不用改这段代码。

## 3. 顺便解决的两个老问题

1. **回声**：外放时麦克风会拾到对方声音。因为回环流拿到的正是"此刻正在播放的对方声音"，它是做 AEC 的**理想参考信号**（比任何盲估计都准）。这条在只有手机采集的方案里是做不到的。
2. **说话人分离**：双轨直接给标签，手机路径那套"问句判定 + 角色推断"的 88% 准确率可以退居二线，只在移动模式下启用。

## 4. 记录在案

这已经是同一天内第二次修正架构判断。两次都错在同一个地方：**把某一端的角色固定死，然后围绕这个固定假设做优化。**

更稳的思路是：**把"谁能采、谁在采、谁在显示"做成运行时可变的仲裁，而不是编译期写死的架构。** v0.3 的采集仲裁状态机（`packages/core/arbiter`）就是按这个思路设计的。

# ADR-003 · 修正 ADR-002 的一处错误判断（loopback 采集）

> 时间：2026-10-26 19:20 ｜ 触发：调研 GitHub 同类项目源码时发现反例

## 被修正的那句话

ADR-002 §"为什么需要一个 sidecar" 第 1 条，我写的是：

> 必须同时请求屏幕视频轨才能拿到音频 → 意味着要抓屏。对一个承诺"只听不看"的产品，这是糟糕的隐私观感。

**前半句对，后半句是我推断过头了。**

## 实际情况（有可运行的代码为证）

`JWM0203/MeetingCopilot`（Apache-2.0，364★）在 Windows 上是这么做的：

```ts
// main process
session.defaultSession.setDisplayMediaRequestHandler((_req, cb) => {
  desktopCapturer.getSources({ types: ['screen'] })
    .then((sources) => cb({ video: sources[0], audio: 'loopback' }));
});

// renderer
const stream = await navigator.mediaDevices.getDisplayMedia({ audio: true, video: true });
for (const t of stream.getVideoTracks()) t.stop();   // 立刻停掉视频轨
```

即：**API 形状要求 `video: true`，但拿到流后立即 `stop()` 视频轨，不采集、不落盘、不推流、不显示**。Windows 上也没有录屏指示灯之类的可见后果（macOS 才有）。

## 修正后的结论

| 项 | 原判断 | 修正后 |
|---|---|---|
| 是否"要抓屏" | 是，隐私观感差 | **否**。仅 API 形状要求，实际不产生画面采集 |
| sidecar 的必要性 | 高（隐私 + 时钟 + 隔离） | **中**（只剩时钟对齐 + 崩溃隔离） |
| M1 第一步 | 先验内建方案 1 天 | **不变，但优先级提到最前**，它是整个 M1 的前置门禁 |
| AEC 的实现载体 | Rust 手写 200 行 WASAPI | **不是 200 行的事**。正经 AEC3 需要原生模块 + 依赖链（project-raven 用 GStreamer + cmake-js 自编 addon）。M2 先用 residualEchoGate 门限顶着，AEC3 延后 |

## 教训

这次的错误类型跟 ADR-002 那次不同：不是"把角色写死"，而是**"把 API 的形参要求当成了运行时行为"**。

以后写架构判断，凡是涉及"某某方案必须付出某某代价"，都要标注这条结论的来源是**代码验证还是文档推断**。推断必须写成"待验证"，不能写进决策记录当成事实。
