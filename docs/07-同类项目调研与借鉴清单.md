## 二、可以直接借的六件事（带出处）

### 1. 系统音频采集：三行关键代码，以及我之前判断错了

`MeetingCopilot/electron/main.ts:529`：

```ts
// Electron's `audio: loopback` display-media source is Windows-only.
session.defaultSession.setDisplayMediaRequestHandler((_request, callback) => {
  desktopCapturer.getSources({ types: ['screen'] })
    .then((sources) => callback({ video: sources[0], audio: 'loopback' }))
    .catch(() => callback({}));
});
```

`MeetingCopilot/src/audio/loopbackCapture.ts`：

```ts
const stream = await navigator.mediaDevices.getDisplayMedia({ audio: true, video: true });
// video track is only there because getDisplayMedia requires it
for (const t of stream.getVideoTracks()) t.stop();
```

> ⚠️ **修正 ADR-002 里我写的一句话。** 我当时说"Electron 内建 loopback 必须同时请求屏幕视频轨，意味着要抓屏，隐私观感差"。前半句对，后半句是我推断过头了：API 形状确实要求 `video: true`，但**拿到流后立刻 `stop()` 掉视频轨，不产生任何可见采集、不写文件、不推流**。Windows 上也没有像 macOS 那样的录屏指示灯。
>
> 所以 200 行 Rust WASAPI sidecar 的**必要性下降了一个档**：它解决的只剩"双轨时间戳对齐"和"崩溃隔离"，不再解决"隐私观感"。M1 那 1 天的内建方案验证，优先级应该提前到**第一件事**。

### 2. PCM 采集的完整正确姿势（含一个多数人会踩的坑）

```ts
const ctx = new AudioContext({ sampleRate: 16000 });   // 直接要 16k，省一次重采样
await ctx.audioWorklet.addModule('pcm-worklet.js');
const node = new AudioWorkletNode(ctx, 'pcm-worklet');
node.port.onmessage = (e) => onPcm(e.data, Date.now());

const mute = ctx.createGain();
mute.gain.value = 0;            // 零增益
source.connect(node); node.connect(mute); mute.connect(ctx.destination);
```

坑在最后三行：**AudioWorkletNode 只有被连向 destination 时才会被拉流**，否则 `process()` 静默地永远不跑。你必须连到 destination，但又不能出声 → 串一个 gain=0。这个坑自己摸索要花半天。

### 3. ASR 的 worker 契约：把"引擎可换"做成结构，而不是承诺

`MeetingCopilot/electron/asr/contract.ts`（文件头写着"Frozen interface… Do not add engine-specific fields here"）：

```ts
backend: 'local' | 'cloud' | 'cloud-realtime'
channel: 'them' | 'me'          // ← 双轨直分，和我们的设计完全一致
pcm: Float32Array               // 16kHz mono
captureTs: number               // 帧末样本的采集时刻，用于对齐
```

它旁边还有 `vad.ts / wav.ts / langRouter.ts / worker.ts`，ASR 跑在 `worker_threads` 里（不阻塞主进程）。这套目录结构**直接照抄**，别自己重新发明。

### 4. VAD：回环轨不需要 Silero

`MeetingCopilot/electron/asr/vad.ts` 的注释一句话点破：

> System-loopback audio is digitally clean (true silence between speech), so RMS + adaptive noise floor is reliable enough. A Silero-VAD probability provider can replace `isSpeechFrame` later without touching the segmenter state machine.

意思是：**回环是数字信号，静音段是真静音**，能量 VAD 就够，省掉一个 ONNX 模型和它的 CPU 开销。只有麦克风轨（有环境噪声）才需要考虑 Silero。我们的双轨架构正好可以分而治之：**回环轨用能量 VAD，麦克风轨用 Silero**。

它把端点检测的参数也全暴露了，这套默认值可以直接拿来当起点：`hangoverMs / minSpeechMs / maxSegmentMs / preRollMs / absSilenceRms / noiseRatio / partialIntervalMs`。

### 5. 首 token 延迟的真正解法：prefix-cache 预热

`MeetingCopilot/electron/main.ts:544` 附近，这段我没想到：

```
// One max_tokens=1 request with the byte-identical stable prefix builds the
// provider-side KV cache, so the first real answer prefills at 0.1x price and
// lower latency. Re-ping when the cache would go cold (same pattern as the ASR 45s keep-warm).
const PREWARM_IDLE_MS = 4 * 60_000;
```

思路是：把"系统提示词 + 简历 + JD"拼成一个**逐字节稳定**的前缀，在面试开始前发一个 `max_tokens=1` 的空请求预热 provider 侧 KV cache，之后每个真实问题的 prefill 都命中缓存 → 首 token 更快、成本降到 1/10。缓存 4 分钟冷掉就再 ping 一次。

这直接命中我之前算的"LLM 首 token 占全链路 55–60%"。**这比换采集端划算得多**，必须抄。

### 6. 两个小但实用的复用点

- **API Key 存储**：`settings.ts` 用 Electron `safeStorage` 加密，并且在 OS 凭据库不可用时置 `weakCrypto: true`、**在保存前就告知用户**。别自己用 base64 糊一层。
- **残余回声门**：`project-raven/src/main/residualEchoGate.ts` —— AEC 之后还会漏一点扬声器串音，它再拿"原始麦克风 vs 最近系统音频"比一次，把仍像扬声器泄露的块丢掉，避免对方的话被记成"我"说的。纯 TS 逻辑，MIT，可移植。

## 三、AEC：验证了我上一轮的判断

`project-raven/README.md`：

```
Echo cancellation — GStreamer webrtcechoprobe / webrtcdsp (WebRTC AEC3),
then a residual echo gate that drops mic chunks that still look like
speaker bleed before they reach STT.
System PCM is the AEC reference.
```

安装步骤是 `brew install gstreamer gst-plugins-{base,good,bad}` → `npx cmake-js compile` 自己编一个 addon。也就是说：**要做正经 AEC，绕不开一个原生模块 + 一套原生依赖链**。

这印证了 ADR-002 的结论——只是实现载体应该是 **Rust/GStreamer sidecar**，而不是我原来想的"纯 Rust 手写 200 行 WASAPI"。范围要重估：AEC 不是 200 行能搞定的，但可以**先用软件门限（residualEchoGate）顶着**，AEC3 留到 M2。

## 四、许可证对照：哪些能 fork，哪些只能看

| 许可 | 项目 | 能不能用 |
|---|---|---|
| **Apache-2.0** | MeetingCopilot、DeLive | ✅ 可以用、可以改、可以闭源衍生（保留 NOTICE + 署名）。**首选基座** |
| **MIT** | project-raven、NexQ、sspOffer | ✅ 最宽松，保留版权声明即可 |
| **GPL-3.0** | pluely | ⚠️ 用了就得整体 GPL 开源。我们本来就开源，勉强可以，但会传染到整个 App |
| **NOASSERTION** | Natively（3082★） | ❌ 自定义条款，**代码一行都别抄**，只当功能地图看 |
| **无许可证** | job-hunt-copilot | ❌ 默认保留全部权利，不可用 |

> 联想到魔方简历也是"Apache 2.0 + 附加条款"，这个圈子的作者普遍对"被人拿去商业化"过敏。我们的开源非商业定位反而是通行证——将来如果要提 PR 或者申请授权，这个身份是加分项。

## 五、重构后的方案：不重复造轮子的三个动作

**动作 1｜基座换血：M1 的采集+ASR 层不再从零写**
以 **MeetingCopilot 的 `electron/asr/` + `src/audio/` 为骨架**（Apache-2.0），把渲染层换掉。它的 loopback 采集、AudioWorklet PCM、worker 契约、VAD、WAV 封装、多引擎路由是成套的，而且已经在 Windows 上跑通。
省下的不是"写代码的时间"，是**踩坑的时间**——loopback 抓不到声、worklet 不触发、16k 重采样、FunASR 模型路径，这些坑它都填过了。

**动作 2｜Coach 模式的设计参考 sspOffer**
它的"RAG 检索面经 → 深挖题 → 连续追问 → 整场评分 → 历史对比"闭环，正好对应我们 M4 的复盘与训练模式。它用 Java/Spring，技术栈不搭，但**出题策略、追问逻辑、评分维度**（结构/深度/表达）是纯产品设计，可以直接借鉴，不必重新想。

**动作 3｜我们自己只做四件没人做过的事**
1. **双端采集仲裁状态机**（手机↔电脑无缝切换，无竞品做）
2. **简历锚定**：思路必须能指到 `experience[].details` 里的具体项目（无竞品做）
3. **合规层**：明示采集、可审计、不规避检测、不给成稿（竞品全部反着做）
4. **魔方简历运行时托管**（无竞品做）

## 七、一句话建议

**把你原来打算自己写的 M1，改成"读三天 MeetingCopilot 的源码，然后 fork 改造"。**
它 Apache-2.0、Windows 优先、双轨 `them/me`、本地 FunASR + 云 ASR 双路、worker 隔离——除了它是给作弊用的（提词器 + 隐身），技术上跟我们的 M1 需求几乎逐条对应。
我们把它那层"隐身"拆掉、把"提词器"换成"思路卡"、再加上双端仲裁和简历锚定，就是一个完整的产品。
