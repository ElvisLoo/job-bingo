02

三种可用形态，一条共同底线

关键设计目标：没有手机也能完整使用。手机是增强，不是前提。所以采集能力必须两端都具备。

主推
DESKTOP ONLY

电脑单机

回环抓对方 + 麦克风抓自己，双轨并行。

  • 数字直采，音质近无损
  • 说话人天然分离
  • 不掏手机
双屏协同
DESKTOP + PHONE

手机当第二屏

电脑负责听和想，手机同步显示。

  • 电脑主采，手机只渲染
  • 省电
  • 低头看手机不显突兀
移动与热备
PHONE ONLY

手机单机

外出、电话面、电脑不可用时兜底。

  • 隔空拾音，准确率打折
  • 问句推断说话人
  • 能推给电脑就推

三条写进代码的自我约束

  1. 只给骨架，不给成稿 —— 单条要点 ≤18 字，禁止输出可朗读的完整段落。
  2. 内容只来自你的简历 —— 每条思路必须能追溯到简历里的某个项目；做不到就直说"这块你简历里没有"。
  3. 不做隐藏 —— 启动即显示"正在聆听"，浮窗有红点，无伪装模式、不改进程名、不规避会议检测。

04

采集仲裁：谁在采，是运行时决定的

两处架构判断连错两次，都错在同一件事：把某一端的角色写死在设计里。所以这一层改成运行时状态机。

1 · 探测
电脑回环是否有信号、手机是否在线、会议进程是否存在
2 · 选举
电脑有信号 → 电脑主采；否则手机接管。同一时刻只一路上行
3 · 无缝切换
保留最近 10 轮上下文，新端接续，不重开会话
4 · 可见
两端都常显"电脑采集 / 手机采集"，可手动强制切换
双轨带来的两个白捡的收益：① 说话人分离不用猜——回环轨就是对方，麦克风轨就是自己，准确率接近 100%，手机端那套 88% 的问句推断可以退居二线。② 回声消除有了理想参考——回环流拿到的正是"此刻正在播放的对方声音"，用它做 AEC 的 reference，比任何盲估计都准。这两件事只有在电脑采集时才成立。
05

两条路径的延迟预算

先说结论：电脑路径比手机路径只快 200–300ms，别指望砍半。它真正值钱的是识别准确率和天然分轨。

环节电脑路径（双轨）手机路径（单轨）
采集缓冲40 ms40 ms
VAD 断句100 ms120 ms
上行 + 流式 ASR250–400 ms
数字直采，识别快且稳		350–550 ms
隔空拾音，易触发重试
问句 / 角色判定30 ms（只看对方轨）60 ms（需推断）
prompt 组装20 ms20 ms
LLM 首 token500–800 ms500–800 ms
渲染 + 推送对端30–60 ms60 ms
合计 P501.0–1.4 s1.3–1.7 s
优化的重点不在采集端。LLM 首 token 占了全链路 55–60% 的预算，ASR 出字占 25%。换采集端能拿回 200ms，但换个快模型能拿回 500ms —— 后者才是该花力气的地方。
06

技术栈：Electron 不动，补一个 Rust sidecar

恢复电脑采音后，ADR-001 里"迁移 Tauri"的第一个触发条件确实被触发了。但结论是不整壳迁移——整个项目只有一个地方需要 Rust：拿 PCM。

为什么不整壳迁 Tauri

收益：包体 120→15MB。成本：托盘、快捷键、多显示器、WebContentsView、亚克力窗全部重写。

为 200 行采集代码重写整个外壳，不划算。

为什么要 sidecar 而不是纯 Electron

Electron 其实能抓 loopback（audio: 'loopback'），但：

① 必须同时请求屏幕视频轨才算拿到音频 → 要抓屏，隐私观感很差；② 双轨时间戳不在同一时钟，对齐误差几十毫秒。

层选型说明
桌面外壳Electron + electron-builder维持不变，不整壳迁移
桌面采集Rust sidecar（~200 行）windows crate 直调 WASAPI，双轨共时钟，独立进程崩溃不影响 UI。stdout 输出二进制帧，stdin 收 JSON 命令
移动外壳Capacitor 7 + Gradle复用 React；录音/前台服务/投屏写 Kotlin 插件
共享逻辑TypeScript（pnpm workspace）含采集仲裁状态机，三处复用
AEC回环流作 reference 的 AEC3回环 = 正在播放的对方声音，理想参考信号
ASR / LLM国内厂商 + OpenAI 兼容可切换，用户自带 Key
简历托管Electron spawn + WebContentsView魔方简历需运行环境，PC 托管其子进程
M1 的正确顺序：先用 Electron 内建 loopback 花 1 天验证"能不能抓到声、延迟多少"，再决定要不要写 sidecar。不要一上来就啃 WASAPI —— 万一目标机器上回环抓不到，你会在错误的地方浪费两周。
07

双端同步：双向

谁跑出思路卡，就推给另一端渲染。哪端是采集端不重要，两端都能显示。

方向场景实现
电脑 → 手机电脑单机，手机当第二屏思路卡 JSON 经局域网 WebSocket 推送，手机原生渲染，延迟 <50ms
手机 → 电脑手机单机，眼睛看大屏同上，方向相反
手机整屏 → 电脑演示、远程求助MediaProjection + H.264，延迟 <200ms（备通道）
简历数据 电脑 → 手机手机端只读锚定标准 Resume JSON 单向同步
08

魔方简历：只装电脑端

它需要运行环境，所以只做在电脑端；手机端不集成编辑器，只接收只读的结构化数据用于思路锚定。

电脑端集成方式

  • Electron 主进程 spawn 它的服务，端口动态分配
  • WebContentsView 内嵌页面，原生外壳里直接编辑
  • 退出时清理子进程；崩溃自动重启最多 3 次
  • 启动检测 Node/Python 依赖，缺什么给一键安装指引

数据最终都转成 Resume

不管它数据存在 localStorage、本地 JSON 还是数据库，最终都抽成内部标准结构。思路引擎只认这个结构——将来换掉魔方简历也不影响主链路。

最大的坑：环境依赖分发。不能让用户先装 Python/Node 再用，M3 前必须评估"内嵌精简运行时"或"引导式一键安装"。
