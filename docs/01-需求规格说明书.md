> 工作代号：**面试副驾**
> v0.3 修订日：2026-10-26
> 平台：Windows（主采集端，双轨） + Android（移动采集端，单轨 + 第二屏）
> 关键变更：**采集双端化、电脑优先仲裁、魔方简历仅电脑端**

## 0. 版本变更记录

| 版本 | 变更 |
|---|---|
| v0.1 | 初稿。Windows 端采音（WASAPI 双轨）、Tauri 2 全栈、投屏方向未定 |
| v0.2 | 数据流反转为"手机采集+推理、电脑纯渲染"；技术栈改 Electron + Capacitor；定位明确为思路提示 |
| **v0.3** | ① **采集双端化**：电脑（WASAPI 双轨）与手机（单轨）都能采能识 ② **电脑优先仲裁**：电脑在线且有声则电脑主采，手机热备 ③ 恢复"没有手机也能用"的单机模式 ④ 魔方简历**仅电脑端**集成（需运行环境，PC 托管子进程）⑤ 新增 Rust 采集 sidecar ⑥ 延迟预算按两条路径分别给 |

## 1. 产品定位

### 1.1 一句话定义

> **不是替你回答，是帮你想起你本来就知道的事。**

听面试官说话 → 转成文字 → 对着你的简历判断他真正想问什么 → 给你 3 条思路骨架 → 半透明浮窗显示 → **你自己组织语言说出来**。

### 1.2 两种使用形态

| 形态 | 设备 | 采集方式 | 说明 |
|---|---|---|---|
| **电脑单机** | 只有 Windows | WASAPI 回环（对方）+ 麦克风（自己），双轨 | **主推**。音质最好、延迟最低、说话人天然分离 |
| **手机 + 电脑** | Android + Windows | 电脑主采，手机做第二屏与热备 | 双屏协同 |
| **手机单机** | 只有 Android | 手机麦克风隔空拾音，单轨 | 外出、电话面、电脑不可用时 |

> 关键：**没有手机也能完整使用**。手机是增强，不是前提。

### 1.3 三种模式

| 模式 | 场景 | 定位 |
|---|---|---|
| **练习** | AI 当面试官，你口头回答，它逐句反馈 | 零风险，新用户入口 |
| **实战** | 真实面试中看思路骨架 | 主场景，需合规声明 |
| **复盘** | 面后回看哪些答得绕、哪些没接住 | 零风险，留存钩子 |

### 1.4 三条写进代码的自我约束

1. **只给骨架，不给成稿。** 单条要点 ≤18 字，禁止输出可朗读的完整段落。
2. **内容只来自你的简历。** 每条思路必须能追溯到简历里的某个项目；做不到就直说"这块你简历里没有，建议坦白没做过"。这同时是治幻觉的技术手段。
3. **不做隐藏。** 启动即显示"正在聆听"，浮窗有红点，没有伪装模式、不改进程名、不规避会议软件检测。

### 1.5 明确不做

- 不做语音朗读、不做即时念稿、不做完整答案
- 不做境外版本（仅中国大陆）
- 不做本地大模型（准确率不够，用户明确否决）
- 不做视频/表情分析、不做题库分发

## 2. 核心用户故事

**US-1｜电脑单机（最常用）**
> 我在电脑上用腾讯会议面试。打开软件，它自己认出了系统里在跑会议，直接开始采音——对方的声音从系统回环里拿，我的声音从麦克风拿，两路分开。1 秒多后屏幕上方的半透明浮窗弹出 3 条思路。我甚至不用掏手机。

**US-2｜手机 + 电脑**
> 我把手机立在旁边当第二屏。电脑负责听和想，手机同步显示，我低头看手机也不会显得奇怪。

**US-3｜手机单机**
> 在咖啡馆用手机接电话面试。掏出手机就能用，隔空听筒里的声音，虽然准确率差一点，但比没有强。

**US-4｜简历驱动**
> 面试前用电脑端的魔方简历模块把简历准备好、贴上 JD。软件标出"这岗位会追问的 5 个缺口"，并按缺口预生成思路卡。面试时问到的，都是我自己项目里的原话。

## 3. 功能需求

优先级：**P0** = MVP 必须；**P1** = 首个正式版；**P2** = 迭代。

### F1A · 电脑端双轨采集（P0，主路径）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1A.1 | 系统声音回环 | WASAPI Loopback 抓默认渲染设备，48k 立体声 → 16k 单声道，CPU <5% |
| F1A.2 | 麦克风采集 | 默认"通信设备"，独立轨道，与回环**不混音** |
| F1A.3 | 双轨时间对齐 | 两轨共享同一时钟，时间戳偏差 <20ms |
| F1A.4 | 缓冲与延迟 | 20ms 缓冲，采集到出 PCM 的端到端延迟 <40ms |
| F1A.5 | 回声消除 | **以回环流为参考信号**做 AEC（回环拿到的正是"正在播放的对方声音"，是最理想的 reference）；戴耳机时自动旁路 |
| F1A.6 | 设备热插拔 | 蓝牙/有线切换、默认设备变更，3 秒内自动重建，UI 状态同步 |
| F1A.7 | 会议软件识别 | 进程 + 音频会话双判定，识别到腾讯会议/钉钉/飞书/Zoom/Teams 时提示"检测到会议，开始聆听？" |
| F1A.8 | 采集指示 | 托盘常驻红点 + 浮窗角标，指示"正在采集"，**不可关闭** |

> **技术选择**：优先用 **Rust sidecar（约 200 行，`windows` crate 直调 WASAPI）**，经 stdin/stdout 或命名管道把两路 PCM 交给 Electron。
> 备选（M1 起步验证用）：Electron 内建 `setDisplayMediaRequestHandler` + `audio: 'loopback'`，一天能跑通，但**必须同时请求屏幕视频轨**才能拿到音频——意味着要抓屏，隐私观感差，且双轨同步难做。因此建议：**先用内建方案验证可行性，再替换成 sidecar**。

### F1B · 手机端单轨采集（P0，移动与热备）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1B.1 | 麦克风采集 | 16kHz / 单声道 / PCM16，缓冲 40ms，CPU <6% |
| F1B.2 | 采音模式 | 近场（放桌上）/ 远场（房间另一头）/ 耳机麦克风 |
| F1B.3 | 增益与降噪 | AGC + RNNoise，可关 |
| F1B.4 | 后台常驻 | 前台服务 + 常驻通知 + 熄屏继续录；厂商白名单引导 |
| F1B.5 | 电量预算 | 连续 1 小时 <12%，机身温度 <42℃ |
| F1B.6 | 单轨说话人推断 | 无回环可参考，靠**问句判定 + 上下文角色推断**区分"我/对方"，准确率目标 >88% |

### F1C · 采集端仲裁（P0，新增）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1C.1 | 优先级策略 | 电脑在线且回环有信号 → 电脑主采；否则手机接管 |
| F1C.2 | 单一上行 | 同一时刻只有一路音频上行至 ASR，**不重复识别**（避免双份 token 与重复思路卡） |
| F1C.3 | 无声判定 | 回环连续 8 秒低于阈值（对方静音/未共享声音）→ 判定"电脑侧无信号"，交由用户确认是否切换 |
| F1C.4 | 无缝切换 | 切换时保留上下文（最近 10 轮问答），新采集端接续，不重开会话 |
| F1C.5 | 可见状态 | 浮窗与手机都显示当前采集端（"电脑采集" / "手机采集"），可手动强制切换 |
| F1C.6 | 双端都在时 | 手机默认只做显示，不采集、不上传，省电 |

### F2 · 语音识别（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F2.1 | 云端流式 ASR | 阿里云实时语音 / 腾讯云 / 讯飞，单句出字 <450ms（电脑路径）/ <550ms（手机路径） |
| F2.2 | 中文准确率 | 电脑路径 WER <6%；手机路径 WER <10% |
| F2.3 | 双轨标签透传 | 电脑路径的识别结果自带 `speaker: me/other` 标签，不靠模型猜 |
| F2.4 | 热词表 | 可导入自定义词（ERP 模块名、INV102、深信服 AC、WQ BRAIN 等）；支持从简历自动抽词 |
| F2.5 | 中英混说 | 正确转写"这个 API 的 throughput"类句子 |
| F2.6 | 断线降级 | 网络中断时暂停推理、保留字幕，恢复后续接，不丢上下文 |

### F3 · 大模型网关（P0，可自定义）

| 编号 | 需求 | 验收标准 |

### F4 · 思路引擎（P0，产品的灵魂）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F4.1 | 触发策略 | 仅当"对方轨出现疑问句"（电脑路径）或"判定为提问"（手机路径）且语句结束后 300ms 触发 |
| F4.2 | 输出结构 | **结论一句话** + **3 条要点（每条 ≤18 字）** + **1 个可引用的自身案例（带项目名）** |
| F4.3 | 简历锚定 | 每条要点必须命中简历中的实体（项目名/技术词/数字），未命中即重写；仍不命中则输出"简历无相关经历" |
| F4.4 | 追问链 | "那后来呢 / 还有吗 / 具体说说" → 沿上一条深化，不重新生成 |
| F4.5 | 追问预判 | 每个问题额外给 1 条"他可能接着问什么" |
| F4.6 | JD 语境 | JD 关键词注入 system prompt，让思路贴岗位 |
| F4.7 | 敏感话题切换 | 薪资谈判 / 离职原因 / 背调 → 切专用模板 |
| F4.8 | 时限控制 | 超 3 秒未出首 token，先显示"思考中 + 已捕获的问题原文" |

| F5.6 | 断线自愈 | 5 秒内重连；断线期间本地正常显示，另一端明确提示"已断连" |

### F7 · 魔方简历模块（P0，**仅电脑端**）

> 已知：GitHub 开源项目，**需要运行环境**（本地部署、网页运行），用于辅助改简历。
> 既然需要环境，就只做在电脑端——手机端不集成编辑器，只接收结构化数据。

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F7.1 | 子进程托管 | Electron 主进程 `spawn` 它的服务，端口动态分配，退出时清理；崩溃自动重启最多 3 次 |
| F7.2 | 内嵌编辑 | 用 `WebContentsView` 内嵌其页面，用户在原生外壳里就能编辑，不切浏览器 |
| F7.3 | 数据抽取 | 从它的导出文件 / localStorage / IndexedDB / 本地 JSON 抽取为内部标准 `Resume` 结构 |
| F7.4 | 环境检测 | 启动时检测 Node/Python 依赖是否就绪，缺什么给出一键安装指引 |
| F7.5 | 手机端只读 | 手机端同步一份简历 JSON（只读），用于思路卡锚定；不在手机上编辑 |
| F7.6 | JD 匹配 | 输出匹配度 + 命中关键词 + **缺口清单** + 每个缺口的应对话术 |
| F7.7 | 派生版本 | 按 JD 重排要点（不新增事实），保留版本历史 |
| F7.8 | 接口抽象 | 定义 `ResumeProvider`，首家实现 `MofangProvider`，将来可换别的简历工具 |

### F8 · 会话复盘（P1）

- 全场问题清单 + 对应的思路卡 + 我的实际表现标记（好/一般/没答上）

- 导出 Markdown / PDF
- **不做**：默认不保留原始音频，只留文字与结构

## 4. 非功能需求

| 维度 | 指标 |
|---|---|
| 端到端延迟 | 电脑路径 P50 ≤1.2s / P95 ≤2.0s；手机路径 P50 ≤1.5s / P95 ≤2.5s |
| 电脑端资源 | 采集时 CPU <8%，内存（含 Electron）<350MB |
| 手机端资源 | 连续 1 小时耗电 <12%，温度 <42℃ |
| 桌面包体 | ≤130MB（不含 Rust sidecar，sidecar 约 2MB） |
| 稳定性 | 连续 2 小时不崩；采集链路异常自动重建；sidecar 崩溃自动拉起 |
| 网络容错 | 弱网（RTT 200ms / 丢包 3%）延迟退化 ≤4s，不崩 |
| 可访问性 | 全键盘可操作；字号 14–24px；高对比模式 |
| 离线能力 | 断网时字幕与思路停摆但界面不崩，恢复后续接；不承诺离线可用 |

## 5. 系统架构

### 5.1 职责划分

```
┌─ 电脑端 Windows（主采集 + 编排 + 渲染）──────────────────┐
│  Rust sidecar：WASAPI 回环 + 麦克风 → 双路 PCM（20ms 缓冲）│
│  Electron 主进程：子进程管理、悬浮窗、快捷键、魔方简历托管  │
│  渲染进程：思路卡渲染、采集端状态、设置                    │
│  Node 侧：VAD、ASR 上行、prompt 组装、LLM 流式             │
└──────────────────────────────────────────────────────────┘
        │                           ▲
        │ WebSocket（局域网）        │
        ▼                           │
┌─ 手机端 Android（移动采集 + 第二屏）─────────────────────┐
│  单机模式：AudioRecord → 问句判定 → 同上链路             │
│  副屏模式：只渲染，不采集不上传                           │
└──────────────────────────────────────────────────────────┘
        │                           ▲
        ▼                           │
┌─ 云端（第三方，可换）─────────────────────────────────────┐
│  流式 ASR  │  LLM 网关  │  复盘分析                      │
└──────────────────────────────────────────────────────────┘
```

### 5.2 代码组织

```
pnpm workspace
├─ packages/core        LLM 网关 / 思路引擎 / 简历解析 / 配对协议 / 采集仲裁状态机（纯 TS）
├─ apps/desktop         Electron + React
│   └─ native/capture   Rust sidecar：WASAPI 双轨采集（~200 行）
└─ apps/mobile          Capacitor + React
    └─ android/         Kotlin 插件：AudioRecord、ForegroundService、MediaProjection
```

**设计原则**：业务逻辑全在 `core`，采集仲裁也是纯 TS 状态机（便于两端共用同一套判定）。平台层只做"拿到 PCM"和"画字"。

### 5.3 延迟预算 · 电脑路径（主）

| 环节 | 预算 |
|---|---|
| 采集缓冲（20ms ×2） | 40ms |
| VAD 断句 | 100ms |
| 上行 + 流式 ASR（数字直采，识别快） | 250–400ms |
| 问句判定（只看对方轨，规则即可） | 30ms |
| prompt 组装 | 20ms |
| LLM 首 token | 500–800ms |
| 渲染上屏 | 30ms |
| 推送手机（若在线） | 30ms |
| **合计** | **1.0–1.4s** |

### 5.4 延迟预算 · 手机路径（备）

| 环节 | 预算 |
|---|---|
| 采集缓冲 | 40ms |
| VAD 断句 | 120ms |
| 上行 + 流式 ASR（隔空拾音，易触发重试） | 350–550ms |
| 问句判定 + 角色推断 | 60ms |
| prompt 组装 | 20ms |
| LLM 首 token | 500–800ms |
| 本地渲染 + 推送电脑 | 60ms |
| **合计** | **1.3–1.7s** |

> **实测预期差异只有 200–300ms**，别指望"换电脑采集"能把延迟砍半。电脑路径真正的收益是**识别准确率**（数字直采、无房间混响）和**说话人天然分离**（不用猜谁在说话）——这两点比省下 200ms 值钱得多。

## 6. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面外壳 | Electron + electron-builder | 亚克力窗、穿透、快捷键成熟；不做整壳迁移 |
| 桌面采集 | **Rust sidecar**（`windows` crate + WASAPI） | 约 200 行，独立进程，崩溃不影响 UI；备选 Electron 内建 loopback（需抓屏，隐私观感差） |
| 移动外壳 | Capacitor 7 + Gradle | 复用 React，原生能力走 Kotlin 插件 |
| 移动录音 | Android `AudioRecord` | 16k/单声道/PCM16；不用 WebAudio（后台被挂起） |
| 共享逻辑 | TypeScript（pnpm workspace） | 三处复用，零平台依赖 |
| AEC | 以回环流为 reference 的 AEC3 | 回环 = 正在播放的对方声音，是最理想的参考信号 |
| ASR | 阿里云 / 腾讯云 / 讯飞 | 国内厂商，中文强，可切换 |
| LLM | OpenAI 兼容 + 多 adapter | 用户自带 Key |
| 传输 | WebSocket + mDNS | 局域网直连；镜像模式走 WebRTC |
| 简历托管 | Electron `spawn` + `WebContentsView` | 魔方简历需运行环境，PC 托管其子进程 |
| 存储 | SQLite（手机）/ electron-store（PC） | PC 只存配置、窗口位置、简历缓存 |
| 打包 | NSIS + APK | GitHub Release 分发，不上商店 |

## 8. 魔方简历集成（仅电脑端）

拿到仓库链接后按顺序判断：

1. **需要什么环境？** Node？Python？还是纯静态？
   → 决定是 `spawn` 一个服务进程，还是直接用 `WebContentsView` 加载本地文件。
2. **数据存在哪？** 浏览器存储 / 本地 JSON / 数据库文件？
   → 决定用注入脚本抽取，还是直接读文件。
3. **能导出什么格式？** PDF / DOCX / JSON？
   → 兜底方案，也是数据抽取失败时的保底路径。

**不论哪种，最终都要转成内部标准 `Resume` 结构**，思路引擎只认这个结构，这样将来换掉魔方简历也不影响主链路。

**环境分发的坑**：如果它依赖 Python/Node 环境，不能让用户先装环境再用——建议 M3 阶段评估「内嵌一份精简运行时」或「引导式一键安装」。这是开源项目分发的常见硬伤。

## 9. 合规（仅中国大陆）

### 9.1 风险画像

| 项 | 状况 |
|---|---|
| 采音 | 录制自己参与的对话；电脑路径是数字直采，手机路径是隔空拾音，两者都不改变法律性质 |
| 上传云端 | 语音属个人信息，上传第三方需告知 + 同意（PIPL 13/17 条） |
| 代答 | **已排除**——思路提示 vs 代答的区别，避开了《劳动合同法》8/26/39 条的欺诈风险 |
| 境外 | **不涉及**——仅中国大陆 |
| 开源 | AGPL-3.0 + README 使用边界声明 |

### 9.2 必须做的四件事

1. **首次使用强制告知**：明确写出"会录制并上传面试音频"，勾选后才能进实战。
2. **提供本地 ASR 选项**：给隐私敏感用户一条"音频不出设备"的路（准确率降，但选择权在用户）。
3. **不做任何隐藏设计**：启动即显示聆听状态，浮窗有红点。
4. **开源前三份文件**：`README`（边界声明）、`LICENSE`（AGPL-3.0）、`PRIVACY.md`（上传什么、传给谁、留多久）。

### 9.3 一条产品建议

加一个**可选的"开场提示音"**——开始聆听时播 2 秒轻音。如果对方问"你那边什么声音"，你可以坦然说"我在用工具记录，怕漏掉您的问题"。这句话说出来，性质就从"偷偷作弊"变成"认真准备"。

## 11. 路线图

| 阶段 | 目标 | 出口标准 | 量级 |
|---|---|---|---|
| **M0 骨架** | Electron 浮窗 + Capacitor 手机壳 + 配对 + 采集仲裁状态机 | 手机按一下电脑浮窗出现 hello；两端状态互见 | ~14 人日 |
| **M1 耳朵** | 电脑双轨采集 + 手机单轨 + 云端流式 ASR + VAD | 电脑路径 WER <6%、出字 <450ms；手机路径可用 | ~28 人日 |
| **M2 大脑** | LLM 网关 + 思路引擎 + 双向同步渲染 | 电脑路径 P95 <2.0s；思路卡命中简历项目名 | ~22 人日 |
| **M3 简历** | 魔方简历子进程托管 + 内嵌编辑 + JD 缺口清单 | 编辑器能用；导出结构化简历；出缺口清单 | ~25 人日 |
| **M4 打磨开源** | 复盘、像素镜像、打包、README/PRIVACY、发布 | 3 台干净机器一次装成功；外网 10 人试用 | ~15 人日 |

合计约 **104 人日**。

> M1 建议的顺序：**先用 Electron 内建 loopback 花 1 天验证可行性，再决定要不要写 Rust sidecar。** 不要一上来就啃 WASAPI。
